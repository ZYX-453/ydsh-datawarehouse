## 一、为什么要先写口径文档

部署手册 1.3 节把「指标口径不清」列为第一难点，原话是「不同人算出不同 GMV」。这不是夸张：
本项目在实机上就出现了同一份数据三种 GMV 的情况——2,471 万、3,700 万、2.66 亿，差别全部来自口径。

所以这一节先把口径钉死，再动 SQL。**口径优先级高于实现**：口径错了，SQL 写得再漂亮也是错的。

### 1.1 五个核心指标的定义

| 指标 | 定义 | 实现位置 | 已知边界 |
|---|---|---|---|
| GMV | `sum(dwd_order.pay_amount) WHERE is_gmv_included = 1` | dwd_order（事实层字段） | 不含待支付 / 已取消 / 退款中 |
| 订单量 | `count(DISTINCT order_id)`，同口径 | dwd_order | 一单多商品只计 1 |
| 客单价 AOV | GMV ÷ 订单量 | ADS 计算列 | 不是「人均」，不要与 ARPU 混用 |
| 活跃用户数 | `count(DISTINCT user_id)`，同口径 | dws_user_agg | 成交口径，非登录口径 |
| 复购率 | 成交 ≥2 单的用户数 ÷ 成交用户数 | ads_kpi_overview / ads_kpi_month | 见 1.3，本项目数据下恒为 100% |

### 1.2 GMV 口径为什么必须带 `is_gmv_included = 1`

第 2 周已把口径下沉到 `dim_order_status.is_gmv_included` 字段（已支付、已完成 = 1；
待支付、已取消、退款中 = 0）。本周所有 DWS / ADS 脚本一律带这个条件，不做例外。

实测差异：

| 统计范围 | GMV | 订单量 |
|---|---:|---:|
| 全部订单（15,000 行） | 约 3,700 万 | 15,000 |
| 仅成交订单（9,992 单） | **24,717,464.96** | **9,992** |

不筛条件的写法会让 GMV 高估约 50%，这是「数出多门」最常见的来源。

### 1.3 复购率为什么会是 100%

实测：1,000 个成交用户共产生 9,992 单，人均 9.99 单，**每个用户的成交订单数都 ≥ 2**，
因此「复购用户数 = 成交用户数 = 1,000」，复购率恒为 100%。

这不是 SQL 写错，是模拟数据生成方式导致的：订单被均匀打散到用户上，不存在只买一次的用户。
**真实业务中该指标的区分度来自「一次性买家」占比**，本项目数据不具备这一特征。
处理方式：指标照算、口径照写，但在报告与答辩中明确标注「本数据集下无区分度」，
不做「复购率 100%，用户粘性极强」这类错误解读。

月度复购率（当月内成交 ≥2 单 / 当月成交用户）仍有区分度，区间为 33.8% ~ 36.8%，
后续分析统一用月度口径。

## 二、本周最重要的一次口径决策：订单金额 ≠ 明细金额

### 2.1 问题是怎么被发现的

按手册步骤 1 写的 ADS 示例是：

```sql
select p.category, sum(o.pay_amount) as sales, count(*) as cnt
from dwd_order o join dim_product p on o.product_id = p.product_id
group by p.category;
```

这段 SQL 有两处问题，跑起来才知道：

1. `dwd_order` 根本没有 `product_id` 字段 → `Error 10004: Invalid column reference`（第 2 周已记录）
2. 就算改成经 `dwd_order_item` 关联，`sum(o.pay_amount) group by 品类` 会把**同一订单的金额在每个品类上各算一次**
   （一笔订单平均 2.5 个商品），实测虚增 **2.5 倍**

于是我去核对「订单实付」与「明细金额」是否一致，结果是**不相等，而且差 10.8 倍**：

| 抽样订单 | 订单实付 | 单价 ×(1-折扣) 合计 | 明细金额合计（含数量） |
|---|---:|---:|---:|
| O2024000001 | 4,374.46 | 14,827.84 | 52,836.35 |
| O2024000002 | 4,378.82 | 11,925.85 | 56,316.82 |
| O2024000003 | 569.90 | 2,561.92 | 8,213.90 |
| 全量合计 | **24,717,464.96** | — | **266,208,760.41** |

三个数字互不相等，比值也不固定（抽样中实付/单价合计从 0.22 到 0.62 波动），
说明**源数据没有按「实付 = Σ 明细」的关系生成**，不存在可反推的一致关系。

### 2.2 三种可选口径与取舍

| 方案 | 品类销售额合计 | 问题 | 结论 |
|---|---:|---|---|
| (a) 直接 `sum(item_amount)` | 2.66 亿 | 与 GMV 差 10.8 倍，同一份报表两套口径 | 否决 |
| (b) 直接 `sum(pay_amount) group by 品类` | 约 6,180 万 | 多品类订单重复计金额，虚增 2.5 倍 | 否决 |
| (c) 订单实付按明细占比分摊 | **24,717,464.96** | 需要一条分摊规则，逻辑稍复杂 | **采用** |

分摊公式：

```
allocated_amount = pay_amount × alloc_w / Σ(alloc_w)     同一订单内
alloc_w = CASE WHEN item_amount > 0 THEN item_amount ELSE 1.0 END
```

- 金额有效时按金额加权，保持原有品类结构比例
- 金额缺失（736 行 NULL、529 行 ≤0，均因数量被置空）时按行平权兜底

兜底规则的必要性：若直接按 `item_amount` 分摊，会有 **130 笔订单（占 GMV 1.25%）**
完全无法归因到商品，品类销售额合计只有 2,440 万，与 GMV 差 30.9 万。
加上兜底后，品类销售额合计 **精确等于 24,717,464.96**，与 GMV 一分不差。

## 三、DWS 汇总层设计

### 3.1 五张表的粒度与用途

| 表 | 粒度 | 分区 | 行数 | 下游用途 |
|---|---|---|---:|---|
| `dws_trade_day` | 日 × 渠道 | `stat_ym`（12） | 1,463 | 日报、渠道对比 |
| `dws_trade_week` | 周 × 渠道 | 无 | 212 | 周会报表、周环比 |
| `dws_store_month` | 月 × 门店 | `stat_ym`（12） | 720 | 门店排名、区域分析 |
| `dws_product_month` | 月 × 商品 | `stat_ym`（12） | 6,993 | 品类/商品分析 |
| `dws_user_agg` | 用户（全周期） | 无 | 1,000 | RFM、用户价值分层 |

粒度覆盖任务书要求的「按天 / 周 / 月、品类、门店、渠道」，映射关系写在 `01_create_dws_tables.sql` 头部。

### 3.2 为什么 DWS 不写死占比和排名

DWS 的职责是「可再聚合」：保留维度、保留明细度量，不写 `share`、不写 `rank`。
理由：一旦在 DWS 固化占比，下游换个筛选条件（比如只看某省份）占比就需要重算，
而 DWS 里的占比是按全量算的，会直接算错。

占比、排名、分层标签一律在 ADS 层做，因为 ADS 的定位就是「面向某个具体场景的成品」。

### 3.3 分区与不分区

- 交易类三张月/日表按 `stat_ym` 分区，与 DWD 的 `order_ym` 对齐，便于分区裁剪
- `dws_trade_week` 只有 212 行、`dws_user_agg` 只有 1,000 行，**不分区**：
  这个量级下分区只会产生大量小文件，反而拖慢查询（第 2 周分桶实验也是同样的结论）

### 3.4 一个容易踩的坑：user_cnt 不能相加

`dws_trade_day` 的 `user_cnt` 是「日 × 渠道内去重」。若直接 `sum(user_cnt)` 求全年活跃用户，
跨渠道、跨天重复的用户会被反复计数。实测按渠道相加得到 4,000+，而真实活跃用户是 1,000。

正确做法：从 `dwd_order` 的 `count(DISTINCT user_id)` 取，或直接读 `dws_user_agg` 的行数。
本项目 ADS 层的 `active_users` 统一取后者。

### 4.6 行为漏斗（结构正确、业务无解释力）

| 层级 | 行为 | 事件数 | 用户数 | 相对浏览 |
|---:|---|---:|---:|---:|
| 1 | 浏览 pv | 34,160 | 1,000 | 100% |
| 2 | 收藏 fav | 5,585 | 995 | 16.35% |
| 3 | 加购 cart | 8,286 | 1,000 | 24.26% |
| 4 | 购买 buy | 11,969 | 1,000 | 35.04% |

漏斗不单调（购买事件数 > 加购事件数），用户级转化率恒为 100%。
根因：行为数据是随机生成的，四种行为对每个用户都独立出现，不存在真实的转化路径。

处理方式：表照建、口径照写，但在本文件、`ads_behavior_funnel` 的 SQL 头注释、
《AI 应用反思》三处明确标注「本数据集下不可用于业务判断」，换真实埋点数据即可出结论。
**不为了让漏斗好看而倒置层级或篡改数据。**

## 五、一致性校验：四路独立计算都必须回到同一个数

这是本周最重要的质量检查。四张 ADS 表分别从不同粒度算 GMV，若口径有偏差，合计就会不一致：

| 计算路径 | 合计（元） | 与 GMV 偏差 |
|---|---:|---:|
| 品类排名 `sum(sales_amt)` | 24,717,464.96 | 0 |
| 省份排名 `sum(gmv)` | 24,717,464.96 | 0 |
| 用户分层 `sum(gmv)` | 24,717,464.96 | 0 |
| 销售日报 `sum(gmv)` | 24,717,464.96 | 0 |
| **基准：`ads_kpi_overview.gmv`** | **24,717,464.96** | — |

门店 Top10 是子集（10/60 家），合计 4,771,219.77 元、占 19.3%，不参与全量校验。

这张表说明了一件事：**分摊口径做对了，四路独立聚合才能收敛到同一个数**。
如果沿用手册的 `sum(pay_amount) group by category`，品类这一路会是 6,180 万，
校验当场就会暴露问题——所以校验不能只看单表对不对，必须交叉验证。

## 六、执行方式

```bash
./run_all.sh week3     # DWS + ADS 全链路（DWD 必须已就绪）
./run_all.sh dws       # 只跑汇总层
./run_all.sh ads       # 只跑应用层
```

执行顺序有硬依赖：`01 建表 → 02~06 逐表加载`，ADS 必须在 DWS 之后。
`sql/dws/04` 会临时建 `stg_order_item_base` / `stg_order_amount` 两张分摊中间表，跑完自动 DROP，
不留在库里干扰 NL2SQL 的 Schema 抽取。
