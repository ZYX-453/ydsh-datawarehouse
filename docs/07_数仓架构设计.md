## 一、分层总体设计

采用 Kimball 维度建模思想 + 业界通行的四层数仓架构：**ODS → DWD → DWS → ADS**。
每层职责单一、只依赖上一层，禁止跨层读取（ADS 不得直接读 ODS）。

```
┌──────────────────────────────────────────────────────────────────────┐
│ 数据源：6 张业务 CSV（用户/商品/门店/订单/订单明细/用户行为）115,209 行  │
└───────────────────────────────┬──────────────────────────────────────┘
                                │  LOAD DATA（CRLF→LF、去 BOM）
┌───────────────────────────────▼──────────────────────────────────────┐
│ ODS 贴源层   ods_*                                                    │
│ 定位：原样接入，不做任何清洗         粒度：与源文件 1:1                │
│ 表：ods_user / ods_product / ods_store / ods_order /                  │
│     ods_order_item / ods_user_behavior                                │
│ 存储：TEXTFILE（保留原始形态，便于回溯与重算）                          │
└───────────────────────────────┬──────────────────────────────────────┘
                                │  清洗 + 标准化 + 去重 + 维度关联
┌───────────────────────────────▼──────────────────────────────────────┐
│ DWD 明细层   dim_* / dwd_*                                            │
│ 定位：清洗后的事实与维度，星型模型     粒度：一行 = 一条业务记录        │
│ 维度表：dim_user / dim_product / dim_store / dim_date                 │
│ 码表：  dim_member_level / dim_pay_type / dim_order_status            │
│ 事实表：dwd_order（按月分区） / dwd_order_item / dwd_user_behavior     │
│ 存储：ORC + SNAPPY                                                    │
└───────────────────────────────┬──────────────────────────────────────┘
                                │  按主题轻度汇总（第 3 周）
┌───────────────────────────────▼──────────────────────────────────────┐
│ DWS 汇总层   dws_*                                                    │
│ 定位：面向主题的宽表，按 日/月 + 维度 聚合   粒度：汇总级              │
│ 规划：dws_trade_day（交易日月汇总）/ dws_user_agg（用户聚合）          │
│ 状态：第 3 周建设                                                     │
└───────────────────────────────┬──────────────────────────────────────┘
                                │  面向指标与报表
┌───────────────────────────────▼──────────────────────────────────────┐
│ ADS 应用层   ads_*                                                    │
│ 定位：直接对接 BI / 大屏的指标结果表      粒度：指标级                 │
│ 规划：ads_kpi_overview / ads_category_sales / ads_province_rank        │
│ 状态：第 3～4 周建设                                                  │
└───────────────────────────────┬──────────────────────────────────────┘
                                │
                    Superset 仪表板 / ECharts 数据大屏
```

## 三、星型模型设计

以订单事实表为核心，四张业务维度围绕，形成标准星型结构：

```
                    ┌───────────────┐
                    │   dim_date    │
                    │  date_key(PK) │
                    └───────┬───────┘
                            │ order_date
┌───────────────┐   ┌───────▼────────────────┐   ┌───────────────┐
│   dim_user    │   │      dwd_order         │   │  dim_product  │
│  user_id(PK)  ├───┤ 订单事实表（核心）      ├───┤ product_id(PK)│
└───────────────┘   │                        │   └───────┬───────┘
  user_id           │ order_id (PK)          │           │ product_id
                    │ order_ym (分区键)       │           │
                    │ pay_amount   ── 度量    │   ┌───────▼────────┐
                    │ discount_amount ─ 度量  │   │ dwd_order_item │
                    │ order_timestamp        │   │  明细事实表     │
┌───────────────┐   │                        │   │ quantity  度量  │
│   dim_store   ├───┤                        │   │ item_amount 度量│
│  store_id(PK) │   └────────────────────────┘   └────────────────┘
└───────────────┘          store_id
```

**度量与属性的划分原则**（也是建模最容易搞混的地方）：

- **度量字段进事实表**：`pay_amount`、`discount_amount`、`quantity`、`item_amount`
- **描述属性进维度表**：`gender`、`member_level`、`category`、`brand`、`province`、`store_name`

**事实表与维度表清单**

| 类型 | 表名 | 主键 | 行数 | 存储 |
|---|---|---|---:|---|
| 维度 | dim_user | user_id | 1,000 | ORC |
| 维度 | dim_product | product_id | 600 | ORC |
| 维度 | dim_store | store_id | 60 | ORC |
| 维度 | dim_date | date_key | 366 | ORC |
| 码表 | dim_member_level | level_name | 12 | ORC |
| 码表 | dim_pay_type | pay_name | 9 | ORC |
| 码表 | dim_order_status | status_name | 12 | ORC |
| 事实 | dwd_order | order_id | 15,000 | ORC + 12 分区 |
| 事实 | dwd_order_item | item_id | 37,549 | ORC |
| 事实 | dwd_user_behavior | behavior_id | 60,000 | ORC + 3 分区 |

## 四、分区与分桶策略

### 4.1 为什么按「年月」而不是「按天」分区

任务书建议按 `order_date` **按天**分区，实际评估后改为**按年月**：

| 方案 | 分区数 | 平均每分区行数 | 评价 |
|---|---:|---:|---|
| 按天（order_date） | ~253 | ~59 | 分区过碎，Tez 下产生大量小文件，反而拖慢查询 |
| **按年月（order_ym）** | **12** | **~1,250** | 分区裁剪有效，文件数可控 |

企业实践中，日分区适用于日均千万级以上的事实表；本项目 15,000 行的量级下，
日分区会让每个文件只有几十行，NameNode 元数据压力和小文件合并开销远大于收益。

> 若数据量增长到日增 100 万行以上，应切换为按天分区 —— 分区粒度必须随数据量调整，
> 这是数仓设计中典型的"没有最优解、只有最合适"。

### 4.2 分桶表实验

按任务书"尝试分桶表"的要求，另建演示表：

```sql
CREATE TABLE dwd_order_bucket (
    ...
) CLUSTERED BY (order_id) INTO 16 BUCKETS
STORED AS ORC;
```

同时开启 `hive.enforce.bucketing=true` 与 `hive.optimize.bucketmapjoin=true`。
**定位为演示级**：分桶在 15,000 行量级下没有性能收益（Map Join 已足够），
主要价值是验证语法与理解 bucket map join 的适用前提（大表 JOIN 大表、连接键高基数）。
若该实验在 Tez 下报错，不影响主链路交付。

## 五、存储与压缩选型

| 层 | 格式 | 压缩 | 理由 |
|---|---|---|---|
| ODS | TEXTFILE | 无 | 保留原始形态，可随时 `DROP`+重载，便于回溯 |
| DWD | ORC | SNAPPY | 列式存储 + 块级索引，较 TEXTFILE 体积约减 70%；SNAPPY 兼顾压缩比与解压速度 |
| DWS / ADS | ORC | SNAPPY | 同上，聚合表列更少、压缩率更高 |

> 未选 PARQUET 的原因：本项目全链路在 Hive 内完成，ORC 与 Hive 的谓词下推、
> 向量化读取集成度更高；若后续引入 Spark/Presto 做跨引擎查询，PARQUET 的兼容性会更好。

## 六、GMV 口径建模（本项目的关键设计）

**问题**：直接 `sum(pay_amount)` 会把待支付、已取消、退款中的订单也算进 GMV，
导致 GMV 虚增约 20%。

**方案**：在 `dim_order_status` 码表中显式建模 `is_gmv_included` 字段：

| 订单状态 | 是否计入 GMV |
|---|---|
| 待支付 | 否 |
| 已支付 | 是 |
| 已完成 | 是 |
| 已取消 | 否 |
| 退款中 | 否 |

清洗时通过 JOIN 把该标记落到 `dwd_order.is_gmv_included`，
后续所有 GMV 统计统一带 `WHERE is_gmv_included = 1`。

**价值**：口径写在维度表里而不是散落在每条 SQL 的 `WHERE` 里。
口径变更时只改码表数据，不用翻遍所有报表 SQL —— 这是"指标口径下沉到模型层"的标准做法。

实测影响：计入 GMV 的订单 9,992 条，GMV = 24,717,464.96 元；
若不加口径（全量 15,000 条），GMV 会虚增约 50%。

## 八、架构演进说明

第 1 周的 `dwd_user` / `dwd_product` 在第 2 周被 `dim_user` / `dim_product` 取代，
原因是第 2 周引入星型模型后，需要按 Kimball 规范区分「事实」与「维度」：
`dwd_*` 只用于事实表（业务过程），`dim_*` 用于维度表（描述实体）。

这是一次**有意的结构重构**，不是命名混乱：
字段基本保留（含第 1 周的可溯源标记），第 1 周文档对字段的描述仍然成立。
因为 ODS 是不可变的唯一真相源，DWD 全量重算不丢失任何数据，重构成本可控。
