# 数据清洗说明（第 1 周：缺失值与重复值）

> 对应任务：子任务 6「缺失值诊断与处理」、子任务 7「重复值检测与去重」
> 脚本位置：`sql/clean/`
> 本文档记录**每类脏数据的数量、处置策略与决策依据**，作为数据质量报告的素材。

---

## 一、清洗总体原则

| 原则 | 说明 |
|---|---|
| 分层隔离 | ODS 层只做结构与格式对齐，保留全部脏数据用于对比；清洗动作一律在 DWD 层完成，ODS 保持原样可追溯 |
| 幂等可重跑 | 所有输出表用 `INSERT OVERWRITE` 重写，脚本可反复执行，结果一致 |
| 留痕可追溯 | 新增 `is_filled` / `is_null` / `ods_dup_cnt` 等标记字段，明确区分「原始值」与「加工值」 |
| 不臆造业务值 | 标识类字段（如邮箱）缺失时保留空值并标记，不填充假数据；仅对数值与枚举做合理填充 |
| 分批推进 | 第 1 周只处理缺失值与重复值；枚举归一化、异常值修正、格式统一留至第 2 周 |

## 二、缺失值处置策略

### 2.1 策略总表

| 表 | 字段 | 缺失数 | 处置方式 | 决策依据 |
|---|---|---|---|---|
| ods_user | age | 51（另有异常 27） | 用**有效年龄中位数**填充 | 数值型且分布偏态，中位数抗极端值；异常值（-3/0/150/200）与空值同等视为无效观测 |
| ods_user | gender | 84 | 填充为「未知」 | 枚举型，无法推断，填语义明确的默认值而非猜测具体性别 |
| ods_user | member_level | 14 | 填充为「普通会员」 | 会员等级是累积结果，无记录者按业务逻辑应为最低等级 |
| ods_user | email | 193 | **保留空值**，新增 `email_is_null` 标记 | 邮箱属联系方式，填充假邮箱会导致后续营销触达失真；标记后可选择性排除 |
| ods_product | launch_date | 11 | 用**同（TRIM 后）类目**其他商品上架日期中位数补全；类目全缺失时回退全表中位数 | 商品上架日期与类目强相关（同类商品通常同期上市），比全局均值更贴近业务实际 |

### 2.2 为什么年龄用中位数而不是均值

脚本先输出了两者的实际差异：

```sql
SELECT med_age, avg_age, valid_cnt, ROUND(med_age - avg_age, 2) AS median_minus_avg
FROM tmp_age_median;
```

即使已过滤到 1～120 的合法区间，年龄分布仍可能偏态。中位数对极端值不敏感，是用户画像场景的通行选择。若均值与中位数接近，两者皆可；若差异明显，必须用中位数并说明理由——**这个判断要在报告里写清楚，是体现数据素养的细节**。

### 2.3 为什么异常年龄也一并填充

《部署操作手册》步骤 8 的验证标准明确要求：

> 「清洗后 `ods_user` 中 `age` 无空值、无负值、无超 120 的异常值」

因此 `age = -3 / 0 / 150 / 200` 这 27 条与 51 条空值同等处理，统一填充。代码中体现为同一个 `CASE WHEN` 条件分支。

## 三、重复值处置策略

### 3.1 重复情况实测

| 指标 | 数值 |
|---|---|
| ODS 订单总行数 | 15,600 |
| 唯一 order_id 数 | 15,000 |
| 重复行数 | 600（重复率 3.85%） |
| 重复组数 | 586 组 |
| 整行完全重复的组数 | 394 组 |
| 主键重复但内容不同的组数 | 192 组 |

### 3.2 两类重复的区别与处理

**① 整行完全重复（394 组）**

所有字段取值完全一致，属**采集或同步环节重复写入**，不是业务事实。处理：直接去重保留 1 条，取哪条都一样。

**② 主键重复但内容不同（192 组）**

同一 `order_id` 下字段存在差异，说明**业务侧对订单做过修改但未做版本管理**。处理：必须按业务规则有依据地取舍，不能随便留一条。

**本项目采用的取舍规则**：

```sql
ROW_NUMBER() OVER (
    PARTITION BY order_id
    ORDER BY
        COALESCE(unix_timestamp(CONCAT(order_date, ' ', order_time), 'yyyy/M/d HH:mm:ss'), 0) DESC,
        pay_amount      DESC,
        discount_amount DESC
)
```

| 优先级 | 排序字段 | 业务含义 |
|---|---|---|
| 1 | 下单时间戳倒序 | 后写入的通常是**修正后**的值，代表最终业务状态 |
| 2 | 实付金额倒序 | 同时间冲突时取金额较大者，避免因去重丢失有效营收 |
| 3 | 优惠金额倒序 | 兜底，保证排序结果确定（避免每次执行结果不一致） |

### 3.3 一个容易踩的坑：排序不能用 order_date 字符串

`order_date` 源格式为 `2024/7/26`（斜杠 + 月日不补零）。**直接字符串排序会得到错误结果**：

```
'2024/12/6'  vs  '2024/7/26'
字符串比较：'2024/1' < '2024/7'  →  12 月被排到 7 月之前（错误）
```

因此必须先拼成完整时间串，再用正确格式解析为时间戳后排序。这是**本脚本里最容易出错、也最容易被忽略的一处**，已在代码中注释标注。

### 3.4 去重未丢失数据的保障

去重最大的风险是误删仍有业务引用的订单。因此脚本做了专项校验：

```sql
-- 明细表引用的每个 order_id，都必须在 dwd_order 中存在
SELECT COUNT(*) AS item_rows_total,
       SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END) AS orphan_item_rows
FROM ydsh_ods.ods_order_item i
LEFT JOIN dwd_order o ON i.order_id = o.order_id;
```

**期望 `orphan_item_rows = 0`**。若不为 0，说明去重删掉了仍有明细的订单，属严重错误。

### 3.5 去重后的验证标准

| 验证项 | 期望值 |
|---|---|
| dwd_order 总行数 | 15,000 |
| 唯一 order_id 数 | 15,000 |
| 剩余重复数 | 0 |
| 删除行数 | 600 |
| 明细表孤儿订单数 | 0 |
| `ods_dup_cnt > 1` 的订单数 | 586（即曾重复的组数） |

## 四、关键技术说明

### 4.1 为什么用 INSERT OVERWRITE 而不是 UPDATE

《第 1 周部署操作手册》步骤 8 给出的示例写法是：

```sql
update ... set age = <均值> where age is null or age < 0 or age > 120;
```

**这种写法在普通 Hive 表上无法执行**，会报错：

```
FAILED: SemanticException [Error 10294]: Attempt to do update or delete
using transaction manager that does not support these operations.
```

Hive 的 `UPDATE` 仅支持 ACID 事务表（ORC 格式 + 分桶 + `transactional=true`，且需开启 `hive.support.concurrency`、`hive.txn.manager` 等多项配置）。本项目采用数仓标准的 `INSERT OVERWRITE` 重写方式，优势是：

- 无事务依赖，普通 Hive 表即可执行
- 天然幂等，脚本可重复运行
- 与离线批处理范式一致，符合企业实践

### 4.2 中位数计算函数选择

使用 `percentile_approx(CAST(age AS DOUBLE), 0.5)`。相比精确的 `percentile()`：

- `percentile()` 要求整型输入，且在大数据量下单点计算内存压力大
- `percentile_approx()` 采用近似算法，内存可控；本数据集仅 1000 行，结果精确

### 4.3 ORC 存储与标记字段

DWD 层表统一使用 `STORED AS ORC` + SNAPPY 压缩，相比 TEXTFILE 可减少约 70% 存储体积，并显著提升后续聚合查询性能。标记字段（`age_is_filled` 等）使用 `INT` 存 0/1，比 `BOOLEAN` 在 Hive 中更稳定且便于聚合统计。

## 五、执行方式

### 一键执行（推荐）

```bash
cd /f/企业项目实战

# 完整流程：ODS + 清洗

# 仅 ODS 层
bash run_all.sh ods

# 仅清洗层（前提：ODS 已就绪）
```

```bash
docker cp sql/clean/01_create_dwd_tables.sql hive-server:/tmp/
docker exec hive-server beeline -u jdbc:hive2://localhost:10000 -f /tmp/01_create_dwd_tables.sql
```

### 执行顺序（不可颠倒）

```
01_create_dwd_tables.sql       建 DWD 表（必须在清洗前）
        ↓

        ↓

        ↓

```
