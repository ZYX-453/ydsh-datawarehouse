## 三、关键成果

1. **汇总层与应用层**。DWS 建成日、周、月三粒度共 5 张表（交易 1,463 行、周汇总 212 行、门店月 720 行、商品月 6,993 行、用户快照 1,000 行）；ADS 固化 8 张成品表，GMV 24,717,464.96 元、订单 9,992 单、客单价 2,473.73 元。品类、省份、用户、日报四路独立聚合的合计均等于该值，用交叉校验证明分摊口径正确。

2. **金额分摊口径**。`dwd_order` 无 `product_id`，商品挂在明细表，而明细的 `item_amount` 是吊牌价，全年合计约 2.66 亿，是实付的 10.8 倍；按手册直连求和，品类这一路会变成 6,180 万。改为按明细金额占比把 `pay_amount` 摊到商品，约 1.3% 明细金额为空或非正，加兜底权重保证 100% 可归因。

3. **预测建模的诚实结论**。建了线性回归、随机森林、梯度提升与两个基线，末 7 天留出集回测。补上常数均值基线后发现：线性回归 MAPE 13.65%、基线 13.19%，**模型没有战胜「直接猜均值」**，全部模型 R² 为负。原因是数据无趋势无季节性（日变异系数 0.230、周内极差 1.078 倍），特征与白噪声一致。交付的是评估框架，不是一组可信数字。

4. **NL2SQL 与 AI 洞察**。链路为「问题 → Schema 组装 → 模型生成 → 守卫校验 → 执行 → 报错回灌自修正」，守卫四道闸把关只读、表白名单、字段存在性与 LIMIT。洞察侧坚持「先算事实再让模型说话」，证据落成 JSON，报告生成后逐个数字回查并输出一致率。

## 四、问题与复盘

**通过率是会骗人的指标。** 配好密钥首跑 NL2SQL 报「7/7 通过」，但第 1 题返回的是空表。两个缺陷叠在一起：`stat_scope` 注释写「如 2024 全年」，真实值是「2024 全年（成交口径）」，模型忠实照抄注释导致 WHERE 匹配不上；而主链路只判「有没有报错」、不判「有没有数据」，静默错误被算成成功。修法是让抽取器对低基数列采样真实取值写进 Prompt（命中 18 表 28 列），并把 0 行也判为失败后回灌重试。只看通过率就收工，交付的会是一个有七分之一概率静默返回空表的接口。

**校验器自己也需要被校验。** 洞察报告首轮一致率仅 96.2%，报了两个「无据」数字。查证发现模型没编造——那是 3,674,468.80 元与 2,932,538.21 元的万元写法，校验器只按「元」比对；改完又报一个 30%，那是行动建议里的告警阈值。两次都是校验器误伤而非幻觉，不查证就写进报告等于把正确表述污名化。最终一致率 100%。

**数字全对，逻辑也可能全错。** 模型对数据提了三个质疑，两对一错。错的是拿「偏离 7 日均值 50%」与「变异系数 0.23」对比断言数据矛盾——两者量纲不同，换算后是 −2.07σ 与 +2.95σ，均在 3σ 内属随机尾部。这类错误能通过全部数字校验，只能靠人复核推理。把 σ 倍数算好放进证据后模型自己就改口，说明它错在缺数据而非缺能力。

**Git 侧**经历一次事故：`.git` 对象库被外部清除，分支与提交全丢。工作区完好，改用干净克隆替换对象库后重做 8 次提交；另发现本环境 `refs/heads/` 下新建子目录的引用会丢失，改用扁平分支名规避。
