## 一、核心设计：先有事实，再让 AI 说话

这套链路最容易做错的地方，是"让模型看一堆数据，然后自由发挥"。
那样得到的文字一定通顺、一定像分析，但数字对不对没人知道。

本项目的做法把顺序倒过来，分三步：

```
① 算事实      从 ADS 取指标 → 算异常（偏离 7 日移动平均的偏离率 + σ 倍数）
              ↓ 产出 insight_evidence.json（40+ 个确定的事实，全部可复算）
② 只喂事实    模型拿到的是「最低日 2024-06-20 为 -2.07σ」这种断言，
              不是原始明细表——模型的自由度被限制在"解释"上，不是"发现"上
              ↓
③ 反查校验    报告生成后，把每一个数字拿回证据里比对，
              输出「有据 / 无据」比例；无据的数字不允许对外使用
```

**为什么第③步是核心**：大模型最擅长的不是算错，而是"编一个看起来很合理的百分比"。
不校验就落进报告，等于把幻觉当分析结论。所以这个脚本的真正价值不是"生成报告"，
而是"生成完还能证明报告里的数字都是真的"。

**为什么第①步要算 σ 倍数**：这是实测踩出来的。第一版只给"偏离 7 日均值 50%"，
模型立刻下结论"数据自相矛盾、可能存在口径问题"——它拿偏离率去和变异系数 0.23 对比，
两者量纲根本不同。补上 σ 倍数（-2.07σ / +2.95σ）后，模型自己就改口写成
"2.95σ 属正常尾部"。**模型错在缺数据，不是缺能力；与其改 Prompt 教它，不如把该算的算好喂给它。**

## 二、异常识别结果

判定方法：计算每日 GMV 相对前 7 日移动平均的偏离率，同时给出全序列 σ 倍数。

| 指标 | 数值 |
|---|---:|
| 统计周期 | 2024-01-01 ~ 2024-12-31（366 天） |
| 全年 GMV | 24,717,464.96 元 |
| 订单量 / 客单价 | 9,992 单 / 2,473.73 元 |
| 日均 GMV | 67,534.06 元 |
| 日 GMV 标准差 | 15,533.43 元 |
| **变异系数（CV）** | **0.230** |
| 周内效应（最强/最弱） | 1.078 倍 |
| 最大单日跌幅 | **−50.99%**（2024-06-15） |
| 最大单日涨幅 | **+94.16%**（2024-03-31） |
| 最低日 GMV / σ | 35,402.70 元（06-20，**−2.07σ**） |
| 最高日 GMV / σ | 113,424.59 元（03-16，**+2.95σ**） |
| 月度环比跌幅最大 | 2024-06（−12.11%） |

跌幅前三：2024-06-15（−50.99%）、2024-03-19（−49.47%）、2024-07-28（−49.20%）
涨幅前三：2024-03-31（+94.16%）、2024-03-16（+70.59%）、2024-06-22（+64.59%）

**σ 倍数是关键**：单看"跌 50%"像崩盘，换算成 σ 才发现最极端的两个点也只在 3σ 以内。
366 天样本里出现 2~3σ 的极值是必然的（单侧 2σ 约每 44 天一次、2.8σ 约每 260 天一次），
所以这批"异常"不需要解释，只需要承认它是随机尾部。

## 三、归因判断：这次必须承认"归不了因"

这是本报告与"看起来很像样"的 AI 分析最大的区别。

单看 −50.99%，很容易编出一个故事：**大促结束后订单回落、竞品促销分流、支付通道故障**……
任何一个都听起来专业。但把这些解释放到数据面前，全部站不住：

| 可能的归因 | 检验结果 | 判断 |
|---|---|---|
| 大促后回落 | 前后 30 天无任何促销痕迹，月度 GMV 极差率仅 12.11% | 不成立 |
| 周内节律（周末效应） | 周内最强/最弱仅 1.078 倍，等于没有季节性 | 不成立 |
| 品类结构性下滑 | TOP1 品类占比 14.87%，TOP3 合计 41.27%，无单一爆品能带动整体 | 不成立 |
| 区域异常 | TOP1 省份占比 11.86%，15 个省份分布均匀 | 不成立 |
| 趋势性衰退 | 全年线性趋势 −0.10%/月，一年只跌 3.6%，不足以解释单日腰斩 | 不成立 |
| 离群数据 | 最极端日 2.95σ，未超 3σ 阈值 | 不成立（是尾部，不是异常） |

**结论：日 GMV 变异系数 0.230，且无趋势、无季节性、无结构集中度——
波动特征与随机过程一致。单日涨跌属于抽样噪声，不具备业务归因价值。**

这次 DeepSeek 的表现值得记录：它没有编故事，而是明确写了
"缺乏促销活动、流量来源、库存与履约等过程数据，**无法判断涨跌的具体成因**"。
这说明只要提示词把"编造"这条路堵死、并给它足够的否定性事实（σ 倍数、极差率、集中度），
模型是能接受"归不了因"这个结论的。

## 四、结构洞察（这部分是有信息量的）

虽然波动归不了因，横截面结构是真实且可用的：

| 维度 | 结论 |
|---|---|
| 品类 | TOP1 运动户外 3,674,468.80 元（14.87%），TOP3 合计 41.27%——结构分散，无单品依赖 |
| 区域 | TOP1 浙江省 2,932,538.21 元（11.86%），TOP3 合计 31.50%——区域性不明显 |
| 用户 | 重要价值客户 252 人，贡献 34.73% GMV——典型二八分布 |
| 漏斗 | buy(11,969) > cart(8,286)，且 buy ≠ 订单量(9,992)——**漏斗不可按常规转化率解读** |

用户维度这条最实用：**约四分之一的人贡献了三分之一以上的成交额**。
RFM 分层里"重要挽留"人群的召回优先级，就建立在这个结构上。

漏斗那条是模型的贡献：它主动指出了 buy > cart 的反常，并进一步发现 buy(11,969) 与
订单量(9,992) 对不上。根因是 `dwd_user_behavior` 的四类行为各自独立采样，
不是同一批用户的串联路径。**这条发现是真实有效的**，后续若要用漏斗做转化诊断，
必须先把埋点口径改成串联。

## 五、事实校验机制（含校验器自身的缺陷）

自动报告里共有 **41 处陈述性数字断言**，逐条回查证据 JSON：

| 项 | 结果 |
|---|---:|
| 陈述性数字断言 | 41 |
| 有据 | 41 |
| 无据 | 0 |
| **一致率** | **100.0%** |
| 决策参数（行动建议里的阈值） | 3（不参与校验） |

校验规则：

```python
# 相对误差 ≤ 2% 记为有据
# 容差不是为了"放宽标准"，而是吸收百分比与小数互写造成的舍入差
# （如 0.1211 与 12.11%，不做容差会全部判为无据，反而失去校验意义）
ok = abs(reported - evidence) / max(abs(evidence), 1e-9) <= 0.02
```

### 5.1 实测中校验器自己错了三次

这是本次最值得记录的部分：**一致率从 96.2% 提到 100%，改的全是校验器，不是模型。**

| 轮次 | 报出的无据数字 | 真相 | 结论 |
|---|---|---|---|
| 第 1 次 | `367.45` | = 3,674,468.80 元 的万元写法 | 校验器不认「万元」单位 |
| 第 1 次 | `293.25` | = 2,932,538.21 元 的万元写法 | 同上 |
| 第 2 次 | `30%` | 行动建议里的告警阈值 | 把决策参数当成数据断言 |

如果不去查证、直接把这三个数当成"模型幻觉"写进报告，等于**把正确的表述污名化**。
一个只输出置信度的校验器，自己也需要被校验。

修法（两个都要）：

1. 候选值增加单位归一化：原值、百分比↔小数、**万元/亿元↔元**；
2. 按 Markdown 章节切分，把「行动建议/方案/措施」类的数字单独计数，
   标注为**决策参数**——它们不是对数据的断言，而是模型自己拍的运营阈值。

### 5.2 这套机制仍然有的局限

1. **只能验"数字"，不能验"结论"**。模型说"因为 6 月大促结束所以 GMV 下跌"，
   数字 12.11% 可能对得上，但因果是编的——校验器不检查因果。
2. **有据 ≠ 相关**。一个数字在证据里存在，不代表用它推出的结论成立。
3. **容差可被利用**。2% 容差意味着把 12.11% 说成 12.3% 也能通过，严格财务口径下不可接受。
4. **单位归一化会放宽边界**。加了万元折算后，`367.45` 这类短数字的匹配范围变大，
   理论上降低了对小数位错误的敏感度。

所以校验的定位是**最后一道筛子，不是质量保证**。

## 六、AI 判断实测：三次质疑，两次对、一次错

这是把"AI 靠不靠谱"从感觉变成证据的地方。同一份证据喂进去，模型提出了三个质疑，
逐个回原始数据核验：

| # | 模型的判断 | 核验方法 | 真相 | 判定 |
|---|---|---|---|---|
| 1 | 单日 ±50~94% 振幅与变异系数 0.23 **不匹配**，可能有口径问题 | 换算 σ 倍数 | −2.07σ / +2.95σ，均在 3σ 内，是随机尾部 | ❌ **错** |
| 2 | 漏斗 buy > cart，**不宜按常规转化率解读** | 查行为表生成逻辑 | 四类行为独立采样，buy(11,969) ≠ 订单(9,992) | ✅ **对** |
| 3 | 复购率 1.0 **需确认口径** | 查用户下单分布 | 1,000 人全在 2 单以上，971 人超 4 单 | ✅ **对，且更严重** |

### 6.1 错的那一次，错在哪

模型把「相对 7 日移动均值的偏离 50%」和「整体变异系数 0.23」放在一起对比，说这两者矛盾。
但这两个量根本不是一回事：

- 变异系数是**相对全序列均值**的离散度 → 反映整体波动水平；
- 50% 偏离是**相对短期基线**的偏离 → 基线恰好处于低谷时会放大。

正确做法是换成 σ：`(111,235 − 67,534) / 15,533 = 2.81σ`。2.8σ 在 366 天里出现一两次完全正常。

**这个错误的危险之处在于"方向听着对"**：它没说假数字，所有数字都真、都来自证据，
只是推理方式错了。读者看到"数据可能有问题"会去查一个根本不存在的问题。
这正是纯数字校验挡不住的那一类错误——它完美通过了 100% 一致性检查。

### 6.2 对的两次，价值在哪

第 2 条是我自己没注意到的。`buy > cart` 在漏斗里是逻辑悖论，
但把它生成出来的脚本（第 2 周）没有告警。模型看出来了，并且顺带发现 buy 与订单量差 2,000。

第 3 条更狠：模型没只说"需确认口径"，它指出了复购率 100% 这件事本身可疑。
顺着查下去才发现，1000 个用户承接 9,992 单（人均 10 单），
**这个指标在这份数据上已经完全没有区分度，任何用它做的分析都是假的**。

### 6.3 所以该怎么用

> 让 AI 做**发现矛盾**（它擅长：跨字段、跨表的不一致它比我扫得快），
> 不让它做**解释矛盾**（它不擅长：会为了"说通"而造一个理由）。

人工复核那一节（报告里的「人工复核记录」）就是照这个分工设计的：
AI 出候选疑点，脚本用可复算的规则给出判定，两者结论不一致时以规则为准。

## 七、AI 应用反思

### 7.1 六个真实存在的局限

**① 数字幻觉：最危险的不是算错，是编得像**

模型不会算错 12.11%，它会直接生成"约 12%"这种看着对的数字。
本次实测它确实没有编造金额，但会把 0.9999 写成"复购率 1.0"——
数字无误，**表述误导**，读者会以为是 1.0% 或 100 分。
校验器对这一类完全无感，因为它检查的是数值不是量纲语义。

**② 因果错觉：模型倾向于给"意义"，而数据可能没有意义**

本次数据无趋势无季节性，正确结论是"归不了因"。
模型在明确被告知"数据不足就说数据不足"之后做到了，但换成开放式提问
（"分析 GMV 为什么跌"）几乎必然给出三个理由——因为提示词本身的假设就是"存在原因"。
**提问方式决定了答案的诚实度。**

**③ 口径幻觉：模型不知道你的业务规则**

`dwd_order` 里待支付、已取消的订单也占行数，直接 `sum(pay_amount)` 会虚增约 50%。
模型看字段名 `pay_amount` 完全可能写出没有 `is_gmv_included = 1` 的 SQL。
**这正是 NL2SQL 必须把口径约束写进 Prompt 的原因**（`05_nl2sql.py` 系统提示词第 3 条）。

**④ 迎合倾向：越流畅越容易被信**

同一份数据，规则版报告读起来干巴巴，反而没人质疑；
LLM 版读起来像分析师写的，读者会自动降低审视强度。
**流畅度与正确性无关，但流畅度会改变人的信任阈值。**

**⑤ 越权建议：模型给的建议往往缺约束条件**

"加大浙江省投放"这类建议，模型不需要知道预算、毛利、履约能力就能说出口。
本报告给出的建议都刻意限定了条件（先补过程数据、按 RFM 召回、阈值化告警），
因为**没有成本信息的建议不构成决策依据**。

**⑥ 推理幻觉（本次新增）：数字全对，逻辑全错**

见 6.1。所有数字都来自证据、全部通过一致性校验，但把两个不同量纲的指标并列对比，
得出"数据矛盾"的错误结论。
**这是现有校验手段最难覆盖的一类，只能靠人复核推理过程。**

### 7.2 偏见来源

| 来源 | 表现形式 |
|---|---|
| 训练语料偏零售电商通用套路 | 默认假设存在大促、季节性与爆品 |
| 提示词框架 | 要求"分析原因"会诱导编造原因 |
| 供给的上下文 | 只给聚合指标、不给明细，模型无法察觉分布异常 |
| 评价方式 | 人偏好"有洞察"的回答，模型会朝这个方向优化表达 |

### 7.3 本项目的三条使用原则

1. **AI 负责表达，不负责事实**：所有数字来自 SQL 与证据 JSON，模型只组织语言；
2. **不可校验的结论不进报告**：宁可写"无法归因"，也不给三个听起来合理的猜测；
3. **人承担最终责任**：报告对外前必须人工复核，特别是因果表述与行动建议——
   模型不会为错误结论负责，签字的人会。

### 7.4 一句话总结

> AI 在这个项目里最大的价值，不是"替我写出分析"，而是**把我从"必须写出点什么"的压力里解放出来**——
> 让我敢在一份报告里写下"这组数据归不了因"。
> 前提是：我用规则校验它的数字，用数据核验它的推理。
