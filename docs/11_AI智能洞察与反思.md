## 一、核心设计：先有事实，再让 AI 说话

这套链路最容易做错的地方，是"让模型看一堆数据，然后自由发挥"。
那样得到的文字一定通顺、一定像分析，但数字对不对没人知道。

本项目的做法把顺序倒过来，分三步：

```
① 算事实      从 ADS 取指标 → 算异常（偏离 7 日移动平均的 z 分数）
              ↓ 产出 insight_evidence.json（30+ 个确定的事实，全部可复算）
② 只喂事实    模型拿到的是「2024-06-15 单日 GMV 环比 −50.99%」这种断言，
              不是原始明细表——模型的自由度被限制在"解释"上，不是"发现"上
              ↓
③ 反查校验    报告生成后，把里面每一个数字拿回证据里比对，
              输出「有据 / 无据」比例；无据的数字不允许对外使用
```

**为什么第③步是核心**：大模型最擅长的不是算错，而是"编一个看起来很合理的百分比"。
不校验就落进报告，等于把幻觉当分析结论。所以这个脚本的真正价值不是"生成报告"，
而是"生成完还能证明报告里的数字都是真的"。

## 三、归因判断：这次必须承认"归不了因"

这是本报告与"看起来很像样"的 AI 分析最大的区别。

单看 −50.99%，很容易编出一个故事：**大促结束后订单回落、竞品促销分流、支付通道故障**……
任何一个都听起来专业。但把这些解释放到数据面前，全部站不住：

| 可能的归因 | 检验结果 | 判断 |
|---|---|---|
| 大促后回落 | 前后 30 天无任何促销痕迹，月度 GMV 极差率仅 12.11% | 不成立 |
| 周内节律（周末效应） | 周内最强/最弱仅 1.078 倍，等于没有季节性 | 不成立 |
| 品类结构性下滑 | TOP1 品类占比 14.87%，TOP3 合计 41.27%，无单一爆品能带动整体 | 不成立 |
| 区域异常 | TOP1 省份占比 11.86%，15 个省份分布均匀 | 不成立 |
| 趋势性衰退 | 全年线性趋势 −0.10%/月，一年只跌 3.6%，不足以解释单日腰斩 | 不成立 |

**结论：日 GMV 变异系数 0.230，且无趋势、无季节性、无结构集中度——
波动特征与随机过程一致。单日涨跌属于抽样噪声，不具备业务归因价值。**

这一条"归不了因"的判断，比编三个理由更有价值：它告诉决策者，**不要为这组数据设 KPI 告警线**，
也不要基于单日波动调整投放。行动建议里据此给出"单日跌幅超 15% 才触发告警"的阈值，
就是为了避免在这种数据上做过度反应。

> 如果这是真实业务数据，排查顺序应是：活动节奏 → 渠道投放 → 支付通道 → 数据延迟（订单未落库）。
> 这四条都在本数据集中不存在，所以只能得出"无归因"。

虽然波动归不了因，横截面结构是真实且可用的：

RFM 分层里"重要挽留"人群的召回优先级，就建立在这个结构上。

## 五、事实校验机制

自动报告里共有 **35 个数字断言**，逐条回查证据 JSON：

| 项 | 结果 |
|---|---:|
| 数字断言总数 | 35 |
| 有据 | 35 |
| 无据 | 0 |
| **一致率** | **100.0%** |

校验规则：

```python
# 相对误差 ≤ 2% 记为有据
# 容差不是为了"放宽标准"，而是吸收百分比与小数互写造成的舍入差
# （如 0.1211 与 12.11%，不做容差会全部判为无据，反而失去校验意义）
ok = abs(reported - evidence) / max(abs(evidence), 1e-9) <= 0.02
```

**这套机制的局限必须说清楚**：

1. **只能验"数字"，不能验"结论"**。如果模型说"因为 6 月大促结束所以 GMV 下跌"，
   数字 12.11% 可能完全对得上，但因果是编的——校验器不检查因果。
2. **有据 ≠ 相关**。一个数字在证据里存在，不代表用它推出的结论成立。
3. **容差可被利用**。2% 容差意味着模型把 12.11% 说成 12.3% 也能通过，这在严格财务口径下不可接受。

所以校验的定位是**最后一道筛子，不是质量保证**。它的作用是挡住"完全凭空编的数字"，仅此而已。

## 六、规则版 vs LLM 版：为什么不能拿规则版冒充 AI

当前 `07_ai_insight.py` 有两条生成路径：

| | 规则模板（当前） | LLM 版（待配密钥） |
|---|---|---|
| 触发条件 | `LLM_API_KEY` 为空 | 配置密钥后自动切换 |
| 内容来源 | 预置句式 + 证据填空 | 模型基于证据自由组织 |
| 归因能力 | **无**——只能陈述事实与"不可归因" | 可给出候选假设与排查方向 |
| 语言质量 | 机械、模板感强 | 流畅自然 |
| 幻觉风险 | **零**（没有生成，只有填空） | 存在，靠第五节校验兜底 |
| 报告首行标注 | `生成方式：规则模板` | `生成方式：LLM (<模型名>)` |

**必须如实说明的三点**：

1. 规则版报告里的每个字都来自模板与证据，**不含任何模型推断**，把它当作"AI 洞察"是名不副实；
2. 所以报告首行强制打印生成方式，且脚本不做任何伪装（不会把规则结果标成 LLM 产出）；
3. 未完成项 ISSUE-08（未配置密钥、LLM 链路未实测）已如实记在 Git 协同记录里，不隐藏。

**为什么坚持这样处理**：如果连"这段文字是谁写的"都说不清，后面所有 AI 治理都是空谈。
标注成本几乎为零，收益是整份报告的可信度。

## 七、AI 应用反思

### 7.1 五个真实存在的局限

**① 数字幻觉：最危险的不是算错，是编得像**

模型不会算错 12.11%，它会直接生成"约 12%"这种看着对的数字。
问题是它可能把"TOP3 品类占比 41.27%"写成"约 45%"——语气同样自信。
**没有数字校验的 AI 报告，本质上不可审计。** 这也是本项目把校验做成强制步骤的原因。

**② 因果错觉：模型倾向于给"意义"，而数据可能没有意义**

本次数据无趋势无季节性，正确结论是"归不了因"。
但模型被要求"分析 GMV 突降原因"时，几乎必然会给出三个理由——
因为提示词本身的假设是"存在原因"。**提问方式决定了答案的诚实度**：
如果问"为什么跌"，得到的是编造；如果问"这组波动是否具备可归因结构"，才可能得到"不具备"。

**③ 口径幻觉：模型不知道你的业务规则**

`dwd_order` 里待支付、已取消的订单也占行数，直接 `sum(pay_amount)` 会虚增约 50%。
模型看字段名 `pay_amount` 完全可能写出没有 `is_gmv_included = 1` 的 SQL，
因为它不知道这个项目把口径下沉到了码表。
**这正是 NL2SQL 必须把口径约束写进 Prompt 的原因**（`05_nl2sql.py` 的系统提示词第 3 条）。

**④ 迎合倾向：越流畅越容易被信**

同一份数据，规则版报告读起来干巴巴，反而没人质疑；
LLM 版读起来像分析师写的，读者会自动降低审视强度。
**流畅度与正确性无关，但流畅度会改变人的信任阈值**——这是 AI 落地最隐蔽的风险。

**⑤ 越权建议：模型给的建议往往缺约束条件**

"加大浙江省投放"这类建议，模型不需要知道预算、毛利、履约能力就能说出口。
本报告给出的三条建议都刻意限定了条件（先补两年数据、按 RFM 召回、阈值化告警），
就是因为**没有成本信息的建议不构成决策依据**。

### 7.2 偏见来源

| 来源 | 表现形式 |
|---|---|
| 训练语料偏零售电商通用套路 | 默认假设存在大促、季节性与爆品 |
| 提示词框架 | 要求"分析原因"会诱导编造原因 |
| 供给的上下文 | 只给聚合指标、不给明细，模型无法察觉分布异常 |
| 评价方式 | 人偏好"有洞察"的回答，模型会朝这个方向优化表达 |

### 7.3 本项目的三条使用原则

1. **AI 负责表达，不负责事实**：所有数字来自 SQL 与证据 JSON，模型只组织语言；
2. **不可校验的结论不进报告**：宁可写"无法归因"，也不给三个听起来合理的猜测；
3. **人承担最终责任**：报告对外前必须人工复核，特别是因果表述与行动建议——
   模型不会为错误结论负责，签字的人会。

### 7.4 一句话总结

> AI 在这个项目里最大的价值，不是"替我写出分析"，而是**把我从"必须写出点什么"的压力里解放出来**——
> 让我敢在一份报告里写下"这组数据归不了因"。
